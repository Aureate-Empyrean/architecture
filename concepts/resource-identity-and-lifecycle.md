# Resource Identity and Lifecycle

How persistent resources are identified, and the lifecycle invariants that keep references trustworthy across deletion, restore, import, merge and module removal. See [ADR 0002](../decisions/0002-uuid-resource-identity.md).

## Resource identity

Every persistent first-class resource has a stable **UUID** identity: Meridian Persons, Organizations and Groups; Mnemosyne Notes, Tasks, Projects and Collections; Atlas Places, Areas and Routes; Lyra, Hermes, Argus and Chronos resources; and other persistent first-class module resources.

Required properties (Established):

- generated by the owning module or client **without coordination through Nexus**;
- suitable for offline/local creation;
- never reused for another resource;
- stable for the lifetime of the resource;
- preserved by backup and restore;
- preserved by migration and import wherever identity is preserved;
- used by all cross-module references.

Database-local numeric IDs may exist inside a module for implementation or performance reasons, but they are **never** public, portable or cross-module identity.

If a UUID version has to be chosen, UUIDv7 is preferred. Encoding, generation details and reference URI syntax are implementation details and remain Open.

A cross-module reference identifies the owning module, the resource type and the resource's UUID. Illustrative only:

```
meridian://person/0192a5d3-7c1e-7b2a-9f4e-3d8c1b6a2e10
```

## References are identity references

A reference points to a resource's identity, **not to a frozen copy of its values**. If the owner edits the resource, every reference sees the edited resource. Consequences:

- Changing the meaning of a widely referenced resource (e.g. moving an Atlas Place that Meridian uses as a historical address) changes it for every referrer. Before destructive or meaning-changing operations, owners should be able to account for incoming references where practical (e.g. show how many resources reference it).
- A module that needs a value as it was at a point in time records that value in its own domain terms (e.g. Meridian's temporal address association), not by copying the referenced resource.

**A reference must never silently point to a different resource** after restore, import or recreation. A recreated resource is a new resource with a new UUID; a restored resource keeps its UUID.

## Resolution states

Resolving a reference yields one of a small set of conceptual states (the wire representation is Open):

| State | Meaning |
|---|---|
| **Available** | The resource exists and the caller may see it. |
| **Unavailable** | The owner cannot currently answer (module disabled, uninstalled, offline, unreachable). |
| **Trashed** | The resource is in a recoverable deletion state. |
| **Deleted** | The resource was permanently deleted. |
| **Not accessible** | The caller lacks the capability to see it. Where the mere existence of a resource is sensitive (e.g. [Janus](../modules/janus.md)), the owner may answer without confirming existence. |
| **Redirected** | The identity was merged into or replaced by another resource; the reference can be followed to the new identity. |

A merge or replacement (e.g. two Meridian Persons merged) may **redirect** the old identity to the surviving one rather than breaking every incoming reference. Redirects are explicit owner decisions, never inferred.

## Destructive operations and module removal

- **Disable/uninstall and destructive data deletion are separate operations.** Uninstalling or disabling a module does **not** delete its user data. Deleting a module's data is a separate, explicit, confirmed user action.
- Incoming references to resources of a removed or disabled module become Unavailable, per [references survive absence](../principles.md).
- Permanent deletion of a resource leaves incoming references resolvable as Deleted, not silently removed.

## Restore

- Restore preserves resource identities.
- **Restore must not immediately trigger destructive retention behavior because restored timestamps are old.** Automatic purges (e.g. [Mnemosyne Trash](../modules/mnemosyne.md#trash) retention) are suspended during restore and reconciled afterwards, with the user in control.
- Derived Nexus state (the reference index, blob usage) is rebuilt or reconciled from modules after restore (see [module-contract](module-contract.md)).
- Backup and restore mechanics are in [backups](backups.md).

## Open questions

- Reference URI syntax, encoding and versioning; wire representation of resolution states.
- How long Deleted and Redirected states are remembered (tombstones), and redirect chains.
- Identity policy for imports that do not preserve identity (e.g. imports from foreign systems create new identities; whether and how old identities can be mapped).
- Blob garbage collection: no global algorithm is chosen; modules report blob usage where applicable ([storage-and-files](storage-and-files.md)).
- Exact reconciliation behavior after restore, including partial (single-module) restore.
